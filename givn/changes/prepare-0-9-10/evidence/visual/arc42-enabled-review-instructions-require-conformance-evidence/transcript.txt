# Instruction: review

Completeness-based coverage review. Goal: every uncovered region is
deliberately classified and resolved. No percentage threshold.

## Preconditions

- **Tasks must be done.** If `givn status --change <id>` shows unchecked
  tasks, warn the user and confirm before proceeding.
- **Never change production code to force a pass.** A failing test is a
  finding to classify or remediate through the loop, not an edit made to turn
  the suite green.

## Review context (mandatory)

Default: perform the review in the current context and record
`Review kind: self-review`. A self-review is not an independent review; do not
label it independent.

For a major change, or when the user requests it, perform the review in exactly
one fresh context: one review subagent, one separate reviewer session, or one
human reviewer. One context covers both the design-review and final-review
obligations for the change. The reviewer must not be the author, must not
receive the author's conversation history, and must review only.

Do not start planning, design, hardening, coverage, implementation, or
additional review subagents. Never start more than one review context.

A change is major when any of these is true, and the change records the reason:

- public contract, CLI or API change;
- persistent data, schema or migration;
- security, privacy or authorization;
- concurrency or distributed behavior;
- architecture boundary or external adapter;
- irreversible or destructive operation;
- multiple capabilities or high blast radius;
- the user explicitly requests an independent review.

If classification is ambiguous, ask the user one question. Do not infer "major"
silently.

The proposal records the requested kind. The design review and the review record
`Review kind`, `Author`, and `Reviewer context`. For an independent review the
reviewer context must differ from the author. A gate that requires independence
accepts only `Review kind: independent`; a self-review is never turned into an
independent claim by gate inference. If independence is required but no fresh
context is available, ask the user; do not silently fall back to self-review.

When the outline addon is enabled, its report is advisory evidence for the one
recorded review context. A self-review uses the self context; an independent
review uses the one independent reviewer. Never create a second outline review
context, require an outline verdict, or treat the outline as a gate.

The review writes only `review.md`. It does not edit production code, tests,
specs, design, tasks, ADRs, glossary, coverage, or README.

## Preflight (before review)

The implementing agent runs the mechanical checks and fixes every failure before
starting the review:

- full `verify.command`;
- full `verify.e2e_command`;
- the project's coverage command with branch instrumentation;
- `givn check review --change <id>`;
- dead code and dead port/contract members;
- receipt freshness;
- canonical proposal and use-case format;
- README badges and other generated evidence.

Do not start the review on a tree that still fails a mechanical check.
The review is for semantic findings, not for discovering work the implementer
can verify deterministically.

After review, fix every finding and verify each one. One targeted closure checks
the recorded findings and material regressions introduced by their fixes; it is
not another open-ended audit and does not require a redundant full-suite run.
Critical defects remain repairable blockers. Minor naming, style polish, and
unrelated findings go to the existing backlog or a separate follow-up batch. A
new non-critical finding goes to the next change. A new critical finding
invalidates the trial rather than extending the loop.

## Step 0 (mandatory, first): implementation evidence check

A change can reach review with every task checked off, the runner exiting
0, and almost nothing actually implemented — if steps were left as
empty/no-op stubs. Mechanical check, before trusting any other artifact:

0. **Verify @e2e tag integrity.** Grep every delta `.feature` file in
   `givn/changes/<change-id>/specs/`. If any scenario's tags were changed
   from including `@e2e` to excluding it, record this as a
   implementation-evidence finding: `@e2e` coverage was planned and then removed
   to bypass the verify-e2e gate. The fix is to restore the `@e2e` tag and
   configure `verify.e2e_command`. Tag removal is independently detected by
   `givn check review` and `givn lint` through tasks.md cross-reference.

1. Grep every step definition file for empty/trivial bodies: `{}`, `() {}`,
   whitespace-only, bare `pass`/`return`, or a body with no reference to any
   assertion library, mock, HTTP client, or domain object. Any match =
   fabricated step.
2. Cross-check every checked scenario has a `COMMIT:` revision. The commit
   must contain the scenario's implementation or regression test; a
   comment-only, whitespace-only, tag-only, task-only, feature-only, or
   transcript-only change is not evidence. A shared batch revision is allowed
   when the `COMMIT:` line names `Batch: <name>`.
2a. A normal change must not use `CHARACTERIZATION` to avoid writing tests.
   Characterization is reserved for reverse-engineering changes.
2b. For high-risk rules (identity, omitted alternative, boundary, lifetime
   limit, precedence), the reviewer may ask for a discrimination proof: revert
   or mutate the production behavior and confirm the test fails. This is a
   risk-based check, not a TDD record; exhaustive mutation testing is not
   required.
2c. A prior run's violation is not a compliance argument. Evaluate against the
   rule, not the archive.

Examples:

  commit: only `# Scenario: ...` in production               -> not evidence
  commit: only `@wip` removed                                -> not evidence
  shared batch: two scenarios, same hash, `Batch: issuance`  -> valid
  shared hash without `Batch:`                                -> invalid
  normal change marked CHARACTERIZATION                       -> invalid
3. Cross-check every component design.md promised (class/service/
   controller/module) exists in the tree. List anything missing —
   incomplete implementation, not a "hard to test" gap.
   Also check that every declared contract is the only surface its consumers
   use; an import of the component's implementation is a finding. Apply `givn
   instructions architecture-principles` when the design declares contracts.
   The composition root and the implementation's own tests are the exceptions.
4. Confirm the runner's strict-mode proof is present with output in
   tasks.md. Missing = every PASS in this change is unverified.
5. **Read every `@e2e` scenario's Then steps.** If a scenario's Then steps
   assert ONLY against a repository/database (no assertion on page content,
   HTTP response, redirect, or CLI output), it is a downgraded e2e scenario
   — an integration test wearing an `@e2e` tag. This is unfinished work,
   not a coverage gap, regardless of the runner reporting GREEN. Record
   each downgraded scenario found.
6. **For a browser-UI capability, read every `@e2e` step definition's
   implementation, not just its assertions.** If the step body sends an
   HTTP request directly, or calls `fetch()`/`XMLHttpRequest` from inside
   the page's JS context, instead of driving the browser (click/type/
   navigate) through a real driver, it is a downgraded e2e scenario even if
   its Then assertion checks page content — the interaction was never real.
   Record each occurrence found.
7. **Identify the exact file(s) `verify.e2e_command` actually invokes.**
   Read the command itself from `givn/commands.yaml`, not just its name — a
   file merely containing "e2e" in its path is not evidence it is bound to
   that command. Then inspect the working state and search the tree for any other
   `@e2e` step implementation for the same capability, including untracked
   or uncommitted files. If more than one implementation exists, read all
   of them. A weaker/downgraded implementation being reviewed while a
   stronger, real-interface implementation already exists elsewhere in the
   tree (committed or not) is itself a implementation-evidence finding — the
   review must use and credit the strongest one, not whichever one
   `verify.e2e_command` happens to point at if that is the wrong one.
8. **Check E2E scope using the canonical specs instruction.** Confirm that
   inventory entries are normalized distinct user actions and that each has one
   E2E scenario. Variants, error cases, and output-affecting flag combinations
   of the same action are regular scenarios. Excess E2E scenarios are a
   implementation-evidence finding.
9. **Confirm the E2E scope is selected explicitly.** When regular and E2E
   verification share one runner command, an explicit scope selection such as
   `GIVN_RESULT_SCOPE` must distinguish the executions. Equal test counts or
   identical command strings do not by themselves invalidate honestly isolated
   scopes. Read the archive verification receipt's per-scope evidence; required
   executions and zero failed or skipped tests remain required, without an
   extra isolation run. Do not re-run the suite in review; the receipt is the
   execution evidence.
10. **Diff the implementation against design.md's stated commands, file
    layout, and framework choices — do not just check they exist.**
    design.md names specific things: the exact `verify.e2e_command` value
    (including its tag-filter flag), exact step-definition file paths (e.g.
    separate files per capability), exact framework/driver. If the
    as-built project deviates from what design.md explicitly named — same
    step file used for both e2e and non-e2e when design.md named two, a
    different or unfiltered command than design.md specified, a different
    driver — and `design.md` was never updated to reflect a deliberate,
    re-reviewed change, this is not a coverage gap or an acceptable
    "practical" shortcut. It is an implementation that silently overrode an
    already-reviewed design decision. Record it as a implementation-evidence
    finding: the fix is to either (a) conform the implementation to
    design.md as originally reviewed, or (b) update design.md with the
    corrected decision and re-run design-review (and reassess the arc42
    chapter table if the change is structural) before the task can be
    considered done — never to silently keep the deviation.
11. **Interaction coverage verification** — cross-reference the interaction
    inventory in the owning use-case document against the design's
    Interaction Coverage Matrix and the actual `.feature` file + step
    definitions:
    a. Read the owning `givn/specs/<usecase-id>/usecase.md` and list every
       entry of its `## Interactions` section — the inventory lives there,
       never in a `.feature` comment block.
    b. Read the design's `Interaction Coverage Matrix` table. Confirm
       every inventory entry appears as a row. Flag missing or extra rows
       as a finding — every interaction must be mapped, no unmapped
       interaction may exist.
    c. For each matrix row, confirm an `@e2e` scenario with a matching
       title exists in the `.feature` file. The scenario title need not be
       identical to the inventory description, but it must clearly cover
       the same interaction.
    d. For each matrix row, grep the e2e step definition file(s) for the
       promised driving mechanism. If the matrix says "Playwright: click
       button X", the step file must import/use Playwright (not `reqwest`,
       not raw HTTP). If the driving mechanism is an HTTP client for an
       API-only capability, confirm the step file uses that HTTP client.
       Mismatch = driving-mechanism finding: the implementation silently
       used a different driver than the reviewed design committed to.
    e. Record the full cross-reference as a table in the implementation evidence check
       section of review.md.
12. Any finding from 1-11 is unfinished work, not a coverage gap. Reopen the
    batch: implement the missing behavior and tests, then refactor — driving
    the real interface per design.md's "Anticipated interface obstacles" fix,
    not by asserting on the repository instead. Do not write `REVIEW: PASS`
    while any finding remains.

Record the result even when clean: "0 empty step bodies found across N files."

## Coverage

Coverage is measured by the implementation preflight with the project's coverage
command and again by the archive against the committed candidate. Review uses
the latest measured evidence and static inspection to classify gaps; do not
write "not measured" as a substitute for classification. If no coverage evidence
exists yet for this change, say so explicitly and classify from inspection —
the archive receipt will carry the measured result. The givn archive
verification and its Cobertura report are authoritative; an external reporter
that cannot execute the project runner is a measurement gap, not absent
coverage.

Do not remove branch instrumentation to raise the line percentage. A line-only
report is a finding; branch coverage is measured when the language supports it.

Redundant unit tests (behaviour already covered by a `.feature` scenario
through the black-box boundary) are removed — the `.feature` file is the
source of truth.

## Classification (three buckets — no fourth bucket)

1. Dead code (YAGNI/KISS) → delete.
2. Missing test coverage → add the tests, implement, refactor, and record the
   batch commit.
3. Legitimately hard to test (rare) → concrete technical justification.

External-input validation is bucket 2 (missing test coverage) until a scenario
or fault-injection test covers it. It is never bucket 3 ("legitimately hard to
test"). A fake boundary makes the case testable; classify it as missing test,
not defensive code.

Example: a provider licence response whose id names another provider. The fake
returns that payload; the scenario asserts refusal. Before the test exists, it
is bucket 2, not "defensive."

These three buckets are exhaustive. **Any classification outside them is
itself a implementation-evidence finding, not a valid outcome** — e.g. "acceptable
for this iteration scope," "sufficient for current scope," "future scope,"
"good enough for now," or any similar invented exception that waves off a
required check instead of fixing it or explicitly justifying it under
bucket 3. A missing or downgraded `@e2e` scenario always classifies as
bucket 2 (missing test coverage) — it can never be excused into a fourth,
undefined bucket. If you find yourself writing a sentence that excuses a
gap without naming one of the three buckets above, stop and reclassify it.

### Use-case scope rejection criteria

A review fails when any of these holds. Each criterion names the observable
document section that proves it.

- **Goal conjunction** — `## Goal` joins two verb phrases, or
  `## Success guarantee` names two outcomes.
- **Missing primary actor** — `## Actors` has no identifiable primary, or
  `## Trigger` does not name them.
- **Placement failure** — `## Capabilities` contains a capability that fails
  the placement test for this goal.
- **Mutation under an observing goal** — a capability's scenarios assert a
  state change while the guarantees declare observation.
- **Extension without a step reference** — `## Extensions` omits its
  main-flow step, or adds a new success outcome.
- **Inconsistent preconditions** — a precondition is established by the flow;
  the success guarantee is assumed; the trigger is a state or desire; an
  unqualified guarantee whose prerequisite is open (`(open: Q<N>)`).
- **Mechanism vocabulary** — `## Goal`, `## Trigger`, or the guarantees name
  a mechanism.
- **Component- or channel-shaped name** — a use-case or capability name names
  a technical component or channel.
- **Oversized leaf** — a leaf's `## Main flow` names three or more actor
  goals.
- **Relationship misuse** — `Extends` without a stated condition; an
  end-user goal placed as a fragment or vice versa.

## Advisory outline evidence

When the `outline` addon is enabled, the outline report supports substantive,
source-confirmed architecture review. It is advisory: it has no verdict, no
metric waiver, no forced reviewer context, and no authority to block review or
archive. A report produced during implementation is reused unless structural
changes have made its relevant evidence stale; only structurally stale
relevant evidence requires rerunning the outline. Nonstructural edits alone do
not require a rerun.

The report covers supported Rust and Python components and their relevant
neighbors. Disclose which languages and components it covers and which it
omits. Unsupported Go or Java components receive direct source assessment using
the same responsibility, interface, dependency-direction, and decomposition
questions; unavailable outline support is not a failure and needs no waiver.

Ask whether responsibilities are cohesive, public interfaces narrow,
dependencies correctly directed, and decomposition understandable. Confirm any
suspected problem against source before drawing conclusions or editing. The
structural call order is not a complete runtime trace, and uncertain or omitted
edges limit the conclusions. The outline alone cannot block review or archive.
