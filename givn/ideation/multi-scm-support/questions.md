# Open questions: multi-scm-support

Parked unknowns. One entry per question; never debate an opinion in place of
a missing answer. Status: `open`, `proposed`, `confirmed`, `answered`, or
`moved`.

| ID | Question | Status |
|---|---|---|
| Q1 | Exact detection semantics: is the order Git worktree -> Fossil checkout -> named refusal correct, or must a project be able to force/declare the backend in `givn/config.yaml`? | confirmed 2026-09-14: detection only, no backend declaration in v1 |
| Q2 | Attribution parity: does Fossil get a `givn`-driven stamping path (wrapper or `--message-file`), does attribution remain Git-only, or does the feature move to an SCM-neutral mechanism? | confirmed 2026-09-14: `givn commit` is the SCM-neutral path; Git keeps the chained `commit-msg` hook as a fallback; Fossil attribution only through `givn commit`; givn stamps its own revisions directly; trailer format unchanged; Fossil is trailer-only (no committer override) |
| Q3 | Clean-state witness: must Fossil treat `EXTRA` files as dirty like Git's `-uall`, or is the Fossil default (only changes that a commit would include) the honest contract? | confirmed 2026-09-14: mirrored strictness — `EXTRA` counts as dirty, so "an untracked file blocks the archive" stays true on both backends |
| Q4 | What replaces TC-32 (project root must equal repository root) for Fossil, where the repository file lives outside the checkout? | confirmed 2026-09-14: the boundary is the checkout root (where `.fslckout`/`_FOSSIL_` lives); the repository file location is irrelevant |
| Q5 | Who commits: does givn keep committing on both backends (write-capable adapter), or does committing move to the human/agent with givn verifying only? | confirmed 2026-09-14: givn publishes the candidate revision (containing the pending receipt) and the finalization revision; per-scenario revisions stay with the developer/agent |
| Q6 | Mixed or nested setups: Git repository inside a Fossil checkout or vice versa — refuse, or define precedence? | confirmed 2026-09-14: detection probes the project root; both markers at the root is an ambiguity refusal; Fossil markers on ancestors are ignored |
| Q7 | `givn init` in a directory with no SCM: scaffold anyway with a warning, or refuse? | confirmed 2026-09-14: scaffold and exit 0 with a named warning that archive and managed upgrade are unavailable |
| Q8 | Do the managed upgrade and migration bundles run on Fossil (two commits, force-staged allowlist) with the same guarantees? | confirmed 2026-09-14: yes — clean preflight, calculated allowlist, and reviewable revisions on both backends; migration-free upgrade publishes one revision |
| Q9 | Does this topic cover kiekste hosting at all, or is the hosting boundary (Fossil server, wiki/tickets/forum, auth) a separate ideation topic? | answered 2026-09-14: out of scope in the frame; kiekste hosting gets its own topic if needed |
| Q10 | Domain vocabulary: do we rename commit/worktree/HEAD to revision/checkout, or keep per-SCM terms in the seam and one neutral term in the domain? | answered 2026-09-14: neutral terms adopted (`revision`, `checkout`, `clean state`, `candidate revision`, `tested revision`, `revision binding`, `upgrade revision`, `plan revision`) and merged into `docs/arc42/12-glossary.md`; per-SCM terms stay in the backend seam |
| Q11 | Integrity check: the `COMMIT:` hash format must accept Fossil hashes (40 hex shown, 64 hex internal); are there length or shape assumptions to remove? | confirmed 2026-09-14: treat the identifier as opaque — non-empty, non-placeholder, non-duplicate; no length or alphabet assumption |
| Q12 | Test strategy: parametrize every fixture over git/fossil/none, or keep Git fixtures and add a dedicated Fossil suite? Is Fossil required in CI? | moved 2026-09-14: design-level decision for the resulting changes, not a domain decision; revisit in the first change's design |
| Q13 | Hook-rejection repair parity: Git keeps the rejected candidate merge staged and unproven; Fossil has no index, so a rejected `before-commit` leaves the working tree unchanged. Does the archive promise the same repair behavior on both? | confirmed 2026-09-14: the promise is "unproven and repairable", not an identical internal state; the existing Git scenario wording becomes backend-neutral |
| Q14 | SCM binary absent: `.git`/`.fslckout` selects a backend whose binary is not installed. Named refusal at selection time, or a backend error at first use? (Frame review F2, gap G11.) | confirmed 2026-09-14: named refusal at selection time, naming the missing executable, before any mutation |
