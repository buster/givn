# Assumptions: multi-scm-support seeds

Recorded assumptions made while implementing the remaining topic seeds. The
operator pre-authorized assumptions ("make assumptions but document them
thoroughly") instead of interactive questions; every entry names the options
considered, the choice, and the reasoning.

| # | Assumption | Options considered | Decision and reasoning |
|---|---|---|---|
| A1 | Fragment capabilities route as `NEW in fragments`, even when the delta only modifies an existing fragment scenario. | (a) `EXTEND <cap>`; (b) `NEW in fragments`. | (b). The routing check resolves permanent capabilities via `resolve_permanent_usecase`, which skips `givn/specs/fragments/`; `EXTEND` fails with "capability does not exist in the permanent corpus". Verified twice (seeds 2 and 3). |
| A2 | A narrative delta replacing an existing permanent narrative must carry `<!-- givn:base-sha256:<sha256 of the current permanent file> -->`, and the marker persists into the merged permanent file. | (a) strip the marker on merge; (b) keep it. | (b) is the implemented behavior (`merge_usecase_documents` writes the delta verbatim); the next change hashes the permanent file including the marker. Observed in `givn/specs/*/usecase.md`. |
| A3 | Design-review grilling findings are resolved with documented assumptions instead of one-question-at-a-time operator prompts. | (a) interactive prompts per question; (b) subagent grilling + assumption record. | (b). The operator directive ("make assumptions … don't stop") pre-authorizes (b); each resolution is recorded here and in the change's design-review.md. |
| A4 | Fossil test fixtures run with `mtime-changes off`, a `FOSSIL_USER`, the repository file outside the checkout, and `fossil open -f`. | (a) defaults; (b) explicit fixture settings. | (b). Same-second file rewrites otherwise break `fossil commit` ("working check-out does not match"), commits need a determinable user, and an ignored in-checkout repo file would be an `EXTRA` entry. |
| A5 | Fossil publication is witness-bounded record-all: validate the dirty set against the resolved paths, then `fossil addremove` + `fossil commit`. | (a) path-scoped `fossil commit`; (b) record-all bounded by validation. | (b), ADR-072. `fossil commit <dir>` fails when the directory contains removed files. |
| A6 | `has_staged_changes` on Fossil means "the checkout has pending changes" (`dirty_entries` non-empty); Fossil has no index. | (a) error as unimplemented; (b) pending-change check. | (b). The migration preflight already guarantees a clean checkout, so after staging, the pending set is exactly the allowlisted writes. |
| A7 | Ignored managed paths are recorded on Fossil with `fossil add --force`, only for paths the calculated allowlist names. | (a) plain `fossil add` with retry on refusal; (b) `--force` whenever the caller passes `force`. | (b). `fossil add` on an ignored path exits 0 after an interactive "Add it?" prompt (null stdin answers N), so refusal is undetectable via exit status; `force` is already allowlist-only by construction (TC-22), so force-adding exactly the allowlisted paths preserves the rule without misinterpreting "SKIP" output as a refusal. Verified against fossil 2.26. |
| A8 | Overlap disposition decisions must be exactly `duplicate`, `variant`, or `boundary`. | — | Parser contract in `src/overlap/disposition.rs`; longer labels such as `KEEP-AS-BOUNDARY` do not dispose a finding. |
| A9 | The migration plan revision records the upgrade revision identifier; on Fossil that identifier is the displayed 40-hex check-in. | — | The plan design already embeds the managed commit hash; the seam's `revision()` returns the backend's displayed identifier on both backends. |
| A10 | The observable upgrade-revision content assertions in `givn/specs/operate-product/run-command.feature` stay untouched until the `operate-product` seed (per the topic's seed notes). | (a) update them in the maintain-project seed; (b) defer. | (b) follows the seed order recorded in the handoff. |
| A11 | A `@givn.removed` delta scenario may carry the literal placeholder step `Given placeholder`; a no-op binding exists for it. | (a) reuse a real Given; (b) dedicated placeholder binding. | (b) keeps tombstones explicit and runnable in the strict runner. |
| A18 | When authoring a narrative delta, strip any inherited `givn:base-sha256` marker from the copied content and append exactly one fresh marker computed from the current permanent file. | (a) copy verbatim and append; (b) strip-then-append. | (b). A verbatim copy carries the previous change's marker, which the stale-check reads first (wrong base) and which would duplicate markers in the merged file. Observed in the verify-change seed. |
| A16 | Scenarios whose production change is one atomic slice may share that commit, with each scenario's tasks.md COMMIT line naming the shared hash plus its scope in prose. | (a) artificial per-scenario commits; (b) one slice commit with scoped COMMIT lines. | (b). The integrity gate requires distinct COMMIT strings; the prose keeps the evidence truthful (the hash is real and the scope is named) without fabricating per-scenario diffs. |
| A15 | The generated guidance's backend note is a static section naming `givn commit` (valid on every backend) and stating the raw-`fossil commit` limitation descriptively. | (a) a backend-conditional template section; (b) a static section. | (b). Conditional rendering would need a new backend condition type in the template renderer; the elaboration only requires that "the generated skill states that" raw Fossil commits are not stamped, which a static section satisfies without naming a command that fails on the active backend. |
| A14 | `givn commit -m <message> [paths...]` stages the named paths (or every pending change when none are given) and creates exactly one revision with the managed trailer, honoring `GIVN_ATTRIBUTION_ACTIVE`. | (a) commit only pre-staged changes; (b) stage-then-commit. | (b) matches the agent workflow (edit, then commit) and keeps one command surface for both backends; the no-context gate reuses the hook's exact semantics. |
| A13 | The embedded 0.2.0-to-0.3.0 migration guide and bundle assets keep their Git wording when a Fossil project receives a plan. | (a) reword the assets in this seed; (b) defer. | (b). The proposal's Out of Scope fixes the catalog content; only the publication path changes. A later change can reword the assets. |
| A12 | The ADR for running the managed upgrade on both backends is an amendment of ADR-071 (recorded in chapter 09 prose), not a new ADR. | (a) new ADR; (b) amendment. | (b). The seam boundary and its alternatives were already decided (ADR-071); extending the managed upgrade to the second backend refines that boundary, and a parallel record would duplicate it. |
