# Givn 0.4.0 to 0.5.0 Migration Guide

This guide migrates a project created with Givn 0.4.x to the Givn 0.5.0
contract. 0.5.0 is a behavioural major release: the embedding-based semantic
similarity gate leaves the default build, the permanent specification corpus
gains a use-case group layout, deterministic discovery replaces embedding
search, capability retirement becomes possible, and several gates tighten.

The guide is an LLM prompt pack. Run the prompts in order from the project
root. The LLM must inspect the project before editing it and must preserve
project ownership boundaries. Unlike 0.4.0, this release **does** require
project-specific migration work; the machine-safe preparation alone is not
sufficient.

## Migration Contract

The 0.5.0 binary performs the machine-safe preparation automatically when all
of these conditions hold:

- `givn/config.yaml` contains the active marker `givn_config_version: "0.4.0"`;
- the project is inside a Git worktree;
- the worktree is clean, including untracked files; and
- `migrate-0-4-0-to-0-5-0` does not already exist in active or archived
  changes.

The automatic preparation updates the managed config scaffold, regenerates
managed agent integrations, and creates two commits:

1. Commit A contains only the managed config, generated skill/command
   targets, and Givn-owned fenced blocks.
2. Commit B contains the maintenance migration change
   (`givn/changes/migrate-0-4-0-to-0-5-0/`) built from the release-owned
   bundle and records Commit A's hash.

Projects whose marker is `0.3.0` or `0.3.1` receive an aggregate migration
(`migrate-0-3-0-to-0-5-0`) that chains the 0.3.0→0.4.0 bundle (a
verify-only phase) with this one. Projects on a 0.4.x patch release whose
marker never reached exactly `0.4.0` get only the managed refresh; run this
guide's prompts manually instead — do not edit the marker by hand to force
bundle materialization.

A project without Git can still follow the prompt pack manually after
creating a clean Git boundary, but no automatic upgrade commit exists and
the LLM must not claim one.

## The 0.5.0 contract in project-visible terms

1. **Feature-free default build.** `spec-retrieval`, `spec-similarity-gate`,
   `cross-encoder-reranker`, and `nli-evidence` are opt-in features.
   `givn spec index`, `spec search`, `spec explore`, and `spec review`
   report retrieval as unavailable in the default build, and the blocking
   semantic-review classification step is compiled out of
   `givn check review`. Deterministic coverage replaces it: exact and
   structural duplicate detection, shape-match overlap findings with an
   enforced disposition vocabulary, and the integrity gates.
2. **Use-case groups.** The permanent corpus layout is
   `givn/specs/<group>/<capability>.feature` with one `group.md` per group
   (Actor, Goal, Main flow, Interactions, Includes, Extends). The flat
   layout still lints and archives, but `givn spec tree`, `spec find`,
   `spec duplicates`, and `spec route` only see the grouped layout.
3. **Capability retirement.** A zero-scenario delta tagged
   `@givn.delta @givn.retired @<capability>` deletes the capability at
   archive time and records a tombstone in `givn/specs/.retired.yaml`.
   review.md must disclose each retirement with a `RETIRE: <capability>`
   line.
4. **Deterministic discovery.** `spec tree` (groups, counts, phrasing
   reuse), `spec find` (lexical AST search), `spec duplicates` (exact and
   structural matches only — the embedding-audit output format is gone),
   `spec route` (advisory EXTEND/NEW candidates), and `spec regroup`
   (grouping proposal, never auto-applied).
5. **Enforced dispositions.** In review.md, the `## Overlap dispositions`
   Decision column accepts only `duplicate`, `variant`, or `boundary`
   (case-insensitive); empty or unrecognised words stop clearing findings.
   `## Overlap dispositions` and `## Split-or-keep` are exact headings the
   review template now ships.
6. **Interaction inventory.** The durable inventory home is the owning
   group's `group.md` `## Interactions` section — one bullet per distinct
   user action. Comment blocks at the top of `.feature` files are no
   longer read. `givn lint` reports per-group interaction over/under
   coverage as warnings; a `@e2e`-tagged Scenario Outline counts once.
7. **Protected review artifact.** Overlays that remove the `review`
   artifact are rejected at load time; use `optional: true` to make it
   skippable instead.
8. **Capability Routing.** Proposals carry a `## Capability Routing`
   table; `givn check review` compares recorded decisions against the
   authored delta. A missing table warns; a present table is strict.
9. **Tighter lint.** Zero-scenario `.feature` files are errors unless they
   are retirement markers; `givn lint --change` runs the overlap scan
   scoped to the change; the group relationship graph (Includes/Extends)
   is machine-checked for dangling targets and cycles.
10. **Merge projection.** One delta may remove a scenario and re-add a
    replacement with the same title.

## Prompt 1: Inventory

Copy the following prompt to the LLM working in the Givn project:

```text
You are migrating a project created with Givn 0.4.x to Givn 0.5.0. Work
from the project root. Do not edit files in this prompt.

Inspect the migration boundary before making any change:

1. Run `git status --short --branch` and `git rev-parse --show-toplevel`.
   Stop if the worktree is not clean or this is not a Git worktree.
2. Read `givn/config.yaml`: record `givn_config_version`, every uncommented
   override, the persisted `skills.targets`, enabled addons, and any
   `artifacts:` entry with `remove: true` (the `review` artifact can no
   longer be removed this way).
3. Run `givn status`, `givn graph`, and `givn addons list`. Record every
   active change and every ejected override under `givn/artifacts/`,
   `givn/skills/`, or `givn/commands/`.
4. For each ejected template or instruction: note whether it still contains
   the retired semantic sections (`## Semantic review classifications`,
   `## Semantic remediation verification`, `## Semantic Review and
   Remediation`) or lacks the new sections (`## Retirements`,
   `## Overlap dispositions`, `## Split-or-keep`, `## Capability Routing`).
5. Determine the permanent corpus layout: flat (`givn/specs/<cap>/<cap>.feature`)
   or grouped (`givn/specs/<group>/<cap>.feature`). Count capabilities.
   List any capability that exists only to describe the semantic engine.
6. For every active change: does its proposal.md carry a
   `## Capability Routing` table? Do its review.md disposition rows use
   free-form decision words? Do its delta `.feature` files carry an
   interaction inventory as a comment block at the top? Any `@wip` left?
7. Search the project (docs, scripts, CI) for invocations of
   `givn spec index`, `spec search`, `spec explore`, `spec review`, or
   parsers of the old duplicate-audit output format.

Return an evidence table with these columns:
`path`, `owner`, `current state`, `0.5.0 action`, `risk`, `verification`.
Do not change a domain specification, step definition, source file, ADR,
Arc42 fact, ejected facet, or user-authored document during inventory.
```

Expected result: a project-specific inventory and no file changes.

## Prompt 2: Machine-safe upgrade

Copy the following prompt only after Prompt 1 confirms a clean Git boundary:

```text
Prepare the machine-safe part of the Givn 0.4.x to 0.5.0 migration.

1. Confirm again that `git status --porcelain --untracked-files=all` is
   empty. If it is not empty, stop without writing.
2. Run `givn upgrade` with the Givn 0.5.0 binary. Do not use `git add -A`.
3. Capture the command output, both commit hashes, and the path of the
   maintenance change (`givn/changes/migrate-0-4-0-to-0-5-0` for a 0.4.0
   source marker; the aggregate id otherwise).
4. Inspect Commit A: it must contain only `givn/config.yaml`, generated
   Givn skill/command outputs for the configured targets, and Givn-owned
   fenced-block changes. If any unrelated path is in Commit A, stop and
   report it; do not repair history automatically.
5. Inspect Commit B: only the migration change. Confirm `.givn-skip`
   contains `specs`, no product feature file was invented, and no
   `DESIGN-REVIEW: PASS`, implementation commit, or `REVIEW: PASS` was
   fabricated.
6. Run `givn skills sync` if any generated file is stale, and record it.

Do not edit domain specs, step definitions, source code, ADRs, Arc42
facts, ejected facets, or user-authored documentation in this prompt.
Return the two commit hashes and the maintenance change path as evidence.
```

Expected result: the config marker identifies 0.5.0, the maintenance change
is active, and generated integrations follow the 0.5.0 contract.

## Prompt 3: Synchronize generated guidance and overrides

```text
Bring every project-owned override to the 0.5.0 contract without
overwriting project-owned intent.

1. For each ejected instruction or template flagged during inventory:
   re-eject the 0.5.0 embedded version (`givn eject <facet>`), then
   re-apply only genuinely project-specific edits on top. Never hand-patch
   the retired semantic sections back into existence.
2. Verify `givn instructions review --change <maintenance-change>` shows
   the deterministic disposition contract (decision words `duplicate`,
   `variant`, `boundary`; exact headings `## Overlap dispositions` and
   `## Split-or-keep`) and no semantic classification contract.
3. Verify `givn instructions specs --change <maintenance-change>` shows
   the interaction inventory policy recorded in the group's `group.md`.
4. Record the resulting override diff in the maintenance change's design
   or tasks evidence.

Do not create a second competing policy source.
```

Expected result: generated guidance and overrides follow the 0.5.0
contract; project intent survives.

## Prompt 4: Project-specific migration decisions

```text
Complete the project-specific migration inside the active maintenance
change. Each decision below is prepared by you and confirmed by the
project owner; none is automatic.

1. SEMANTIC FEATURES. Decide with the owner whether embedding retrieval
   is still wanted. Default: accept the feature-free build. If retained,
   document the explicit build invocation
   (`cargo install givn --locked --features spec-retrieval,...`) in the
   project README and keep `givn spec index` in the workflow. Record the
   decision in the maintenance change.
2. CORPUS LAYOUT. If the corpus is flat: run `givn spec regroup --format
   json`, present the proposal, and apply only the confirmed grouping —
   `git mv givn/specs/<cap>/<cap>.feature
   givn/specs/<group>/<cap>.feature` (renames, never delete+add), remove
   emptied directories, scaffold one `group.md` per group, and write real
   Actor/Goal/Main flow/Interactions prose. Capabilities with no dominant
   command surface are `«include»` fragments and go into a support-style
   group. Record `«include»`/`«extend»` relationships one bullet per
   target on the depending side, with exact names, acyclic. Update any
   document that teaches the old flat paths.
3. INTERACTION INVENTORIES. Move inventory comment blocks from `.feature`
   files into the owning group's `group.md` `## Interactions` section,
   one bullet per distinct user action. Run `givn lint` and reconcile
   each group's declared interaction count with its implemented `@e2e`
   count.
4. RETIRE DEAD CAPABILITIES. For each capability that only described
   removed behaviour, author a zero-scenario delta tagged
   `@givn.delta @givn.retired @<capability>`, add a
   `RETIRE: <capability> — <reason>` line to review.md, and archive
   through the normal workflow.
5. DISPOSITION VOCABULARY. In every active change's review.md, replace
   free-form Disposition values with exactly one of `duplicate`,
   `variant`, `boundary`, and make the section headings exactly
   `## Overlap dispositions` and `## Split-or-keep`.
6. PROTECTED ARTIFACT. If `givn/config.yaml` removes `review`, replace
   the patch with `optional: true` (if a skip is intended) or delete the
   patch. Confirm `givn check review` still lists `review` in the
   effective manifest.
7. CAPABILITY ROUTING. For each active change still in flight, run
   `givn spec route --change <id>` and fill the proposal's Capability
   Routing table with recorded decisions.
8. WORKFLOW REFERENCES. Update project docs and scripts that invoke
   `givn spec index`/`search`/`explore`/`review` unconditionally or parse
   the old duplicate-audit output. The new `givn spec duplicates` prints
   `scanned permanent corpus: N exact/structural match(es)` or a JSON
   array with kind/left_file/left_title/right_file/right_title.

Apply specification edits through the normal Givn lifecycle, one concern
per commit. Do not claim unverified work. Never weaken a gate to make a
check pass.
```

Expected result: the layout decision applied or explicitly deferred, the
semantic-feature decision recorded, and every gate-relevant artifact on
the 0.5.0 contract.

## Prompt 5: Verify and archive

```text
Prove and close the Givn 0.4.x to 0.5.0 migration.

1. Run `givn lint`. Confirm zero errors. Review every warning (shape
   match, subset, long scenario, singleton group, interaction coverage)
   and disposition it with a valid decision word where the review
   contract requires it.
2. Run the project's `verify.command` and `verify.e2e_command`.
3. Post-migration smoke: `givn spec tree` lists groups with Actor and
   Goal; `givn spec find <known-term>` returns the expected hit;
   `givn spec duplicates` runs without a model or index;
   `givn spec route --change <maintenance-change>` runs (advisory only).
4. For every active change, run `givn check review --change <id>` and
   resolve every blocking finding. In a feature-free build the semantic
   gate is absent; the structural, integrity, retirement-disclosure, and
   routing gates remain.
5. Confirm `givn/config.yaml` loads and the effective manifest still
   contains `review`.
6. Complete the maintenance change through design-review, tasks, and
   review with real evidence, then archive it:
   `givn archive --change migrate-0-4-0-to-0-5-0` (or the aggregate id).
7. After archive: `givn status` clean, no synthetic migration feature
   under `givn/specs/`, `givn/specs/.retired.yaml` (if retentions ran)
   lists only genuinely retired capabilities, and the final Git history
   separates the managed commit, the migration change, and the
   project-specific commits.

If any check fails, keep the maintenance change active, describe the
blocker, and continue through the appropriate Givn artifact. Do not
weaken a gate by removing tags, deleting evidence, or replacing a
real-interface test with a lower-level assertion.
```

Expected result: the maintenance change is archived as operational history
and the project runs the 0.5.0 contract with evidence for every decision.

## Completion Definition

A project is migrated when all of the following are true:

- the package in use is Givn 0.5.0 and `givn_config_version` matches;
- generated guidance and every project override follow the 0.5.0
  contract (no retired semantic sections; the new sections present);
- the corpus layout decision is applied and the grouped discovery tools
  work, or the deferral is recorded with the flat-layout consequences
  understood;
- the semantic-feature decision (default opt-out, or documented opt-in)
  is recorded in the project;
- every active change's evidence satisfies the deterministic gates with
  the enforced disposition vocabulary;
- project-owned content, ADRs, and Arc42 facts survive intact; and
- the maintenance change is archived without a synthetic capability in
  `givn/specs/`.
