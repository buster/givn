# Givn 0.8.0 to 0.9.0 Migration Guide

This guide migrates a project created with Givn 0.8.x to the Givn 0.9.0
contract. 0.9.0 changes where the rules live: installed skills and commands
become triggers that direct the agent to `givn instructions <id>`, which
serves the built-in rules at call time, and project-specific rules move to
the project-owned `extensions:` map in `givn/config.yaml`.

The guide is an LLM prompt pack. Run the prompts in order from the project
root. The LLM must inspect the project before editing it and must preserve
project ownership boundaries.

## Migration Contract

The 0.9.0 binary performs the machine-safe preparation automatically when all
of these conditions hold:

- `givn/config.yaml` contains the active marker
  `givn_config_version: "0.8.x"` (the exact patch does not matter);
- the project is inside a supported SCM checkout (Git or Fossil);
- the checkout is clean, including untracked files; and
- the maintenance change for the route does not already exist in active or
  archived changes.

The automatic preparation updates the managed config scaffold, regenerates
managed agent integrations — an installed file that still carries a full rule
copy is rewritten to the direction — and creates two commits:

1. Commit A contains only the managed config, generated skill/command
   targets, and Givn-owned fenced blocks.
2. Commit B contains the maintenance migration change built from the
   release-owned bundle and records Commit A's hash.

Projects whose marker is older receive an aggregate migration that chains the
intervening bundles in order. A project without a backend can still follow
this guide manually after creating a clean checkout boundary, but no automatic
upgrade commit exists and the LLM must not claim one.

## Execution model

The maintenance change carries the work directly: it edits one project-owned
configuration file and verifies the result. It has no product specification
and no corpus repairs. The normal Givn gates still apply — derive the change's
tasks from the inventory, run design-review before tasks, complete review and
archive.

A project that never customized a generated rule file and never hand-edited
the managed `givn-project` block in AGENTS.md has nothing to move: record the
checked file list as the "none found" finding and complete the verification.

## Prompts

### Prompt 1 — Inventory the displaced rules

> The pre-upgrade revision is `{{UPGRADE_COMMIT}}^`. List the managed rule
> paths in it — `<target>/skills/givn-*/SKILL.md` for every target in
> `skills.targets`, and `<target>/commands/givn-*.md` plus `grill-*.md` for
> the command-owning targets. Map each file to its instruction id (for
> example `givn-spec` → `specs`, `givn-implement` → `tasks`). For every file,
> read the old content and the served instruction (`givn instructions <id>`)
> and collect every rule statement the old file carries and the served
> content does not. Compare semantically — reworded or moved built-in rules
> are not displacements. Also inventory edits inside the
> `<!-- givn:begin:givn-project -->` block of AGENTS.md in the pre-upgrade
> revision. If the old files were never tracked (`rules: local-only`), ask
> the human for the project-specific rules they kept.

### Prompt 2 — Classify each displaced statement

> Classify every collected statement: a project rule to keep (an extension
> entry), stale built-in text to drop with its reason, or uncertain — ask the
> human, one question at a time, with the old text and the candidate
> dispositions. Record one inventory row per statement in the maintenance
> change's `design.md`: old file, displaced statement, classification, target
> instruction id. Record the checked file list and a "none found" line when
> there are no displacements.

### Prompt 3 — Record the extensions

> Add the kept rules to the `extensions:` map in `givn/config.yaml` — an
> instruction id maps to a list of non-empty rule strings. List a rule under
> several ids to extend each of them. Do not edit a project-owned replacement
> (`givn/artifacts/<id>/instructions.md`); the extension extends it. Verify
> each extended instruction with `givn instructions <id>`: the content must
> end with the marked `## Project extension` section carrying the rules in
> config order, with the built-in rules unchanged above it.

### Prompt 4 — Verify and archive

> Spot-check the installed files in every configured target: trigger and
> direction only, no rule copy, no extension text. Confirm the extension
> lives only in `givn/config.yaml`. Run the project's suite
> (`verify.command`). Derive the change's tasks from the inventory rows and
> complete the normal gates — design-review before tasks, review, archive. Do
> not claim a review or implementation result the evidence does not carry.

## Completion boundary

The maintenance change is complete when every displaced statement has a
disposition (an extension entry, a recorded stale-drop reason, or a named
follow-up change), each extended instruction serves its rules under the
marked section, the installed files carry only trigger and direction, and the
change has archived through the normal gates.
