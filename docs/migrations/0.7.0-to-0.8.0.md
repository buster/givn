# Givn 0.7.0 to 0.8.0 Migration Guide

This guide migrates a project created with Givn 0.7.x to the Givn 0.8.0
contract. 0.8.0 is a behavioural release: the use-case model, the persona
model, and the ADR qualification gate are hardened, and several smaller
authoring rules are new.

The guide is an LLM prompt pack. Run the prompts in order from the project
root. The LLM must inspect the project before editing it and must preserve
project ownership boundaries. The machine-safe preparation alone is not
sufficient: this release requires project-specific work on the artifacts the
project already owns.

## Migration Contract

The 0.8.0 binary performs the machine-safe preparation automatically when all
of these conditions hold:

- `givn/config.yaml` contains the active marker
  `givn_config_version: "0.7.0"`;
- the project is inside a supported SCM checkout (Git or Fossil);
- the checkout is clean, including untracked files; and
- `migrate-0-7-0-to-0-8-0` does not already exist in active or archived
  changes.

The automatic preparation updates the managed config scaffold, regenerates
managed agent integrations, and creates two commits:

1. Commit A contains only the managed config, generated skill/command
   targets, and Givn-owned fenced blocks.
2. Commit B contains the maintenance migration change
   (`givn/changes/migrate-0-7-0-to-0-8-0/`) built from the release-owned
   bundle and records Commit A's hash.

Projects whose marker is older receive an aggregate migration that chains the
intervening bundles in order. A project without a backend can still follow
this guide manually after creating a clean checkout boundary, but no automatic
upgrade commit exists and the LLM must not claim one.

## Execution model

The maintenance change is the **inventory and plan**, not the repair site.

1. **Full retrofit.** Nothing is grandfathered; every permanent use case,
   persona, and accepted ADR is brought into the model.
2. **Inventory and plan.** The maintenance change records every deviation
   with its disposition and the follow-up change that will fix it; it edits
   no corpus artifact except the term collision-check cells.
3. **Archive timing.** The maintenance change archives once every deviation
   names a follow-up change (or an in-flight one). The inventory is the
   durable record; the migration is complete when the follow-ups archive.
4. **ADR scope.** Accepted records are re-qualified in the maintenance
   change; a `proposed` record is listed against the owning change that must
   qualify it before that change archives. An archived change is never named
   as a pending follow-up.
5. **Non-qualifying ADRs.** The rationale moves once to one canonical home,
   the record leaves the register and both indexes, and the maintenance
   change keeps the audit note. It is never copied into
   `docs/arc42/adr/archive/`.
6. **Renames.** Component- and channel-shaped capability and use-case names
   are renamed in the follow-up, which moves the `.feature` file and updates
   every reference; one use case per follow-up change.
7. **Term evidence.** Every existing `confirmed` term gets its search re-run
   and the commands and hit counts recorded; a collision found becomes a
   follow-up that renames or rejects the term.

The bundle's `design.md` inside the maintenance change is the authoritative,
self-contained procedure. The summary below is for human orientation.

## The 0.8.0 contract in project-visible terms

1. **Use-case model.** A use case is a contract between one primary actor and
   the system. Eight scoping rules apply: one goal and one primary actor;
   goal-shaped names; level discipline (`!` owns capabilities, `+` owns only
   child leaves, an oversized leaf is promoted and split); mutation
   containment; extension discipline; precondition and flow consistency;
   implementation independence; relationship semantics. Ten rejection
   criteria (R1-R10) name the observable section that proves each failure.
2. **Personas.** A new persona exists only when it differs in authority
   boundary, evaluation capability, or own vocabulary. Files carry a stable
   core plus an append-only running record and a dated topic-stances
   appendix. Reuse comes first: inventory, match by ID or justify a new
   segment, keep reused topic files record-only, and append-merge at handoff.
   `givn lint` reports dangling `## Personas` references as `[PERS ]`
   advisories; a visual change's `PERSONAS:` value is enforced by
   `givn check review`.
3. **ADR qualification.** Three falsification tests join the five mandatory
   dimensions: single-change reversibility, no multi-change constraint, and
   the product-behavior exclusion. The structured verdict is recorded in the
   change assessment before any MADR is created; the ADR template ships
   blank; design-review requires the cheaper-home challenge for every
   proposed new ADR.
4. **Dialog policy.** `givn instructions dialog` is the canonical policy for
   every interactive question: named artifacts, four-part option treatment,
   cross-reference glosses, standalone answerability, rejected alternatives,
   one question at a time.
5. **Change seeds.** Seeds carry a status line (`ready`, `proposed by`,
   `implemented in`, `superseded by`, `withdrawn`) and a content schema;
   `givn lint` reports a missing or contradicted status as `[SEED ]`.
6. **Term records.** `domain-terms.md` entries carry a status, definition,
   contrast, first use, and a recorded collision check; `confirmed` requires
   the pasted commands and hit counts.
7. **Guarantees and the ledger.** Unresolved prerequisites are marked
   `(open: Q<N>)`; proposal questions carry `D<n>` IDs and the design records
   `Decides D<n>` for each.
8. **Severity and routing.** Lint findings carry `advisory`, `finding`, or
   `blocking`; `givn spec route` reports `signal` or `no signal` with
   ownership-weighted scoring.

## Prompt pack

### Prompt 1 — Inventory the use-case model

> Read the migration bundle's Phase 1 in
> `givn/changes/migrate-0-7-0-to-0-8-0/design.md`. Build the use-case
> inventory table: one row per permanent use-case document with the failing
> scoping rules and rejection criteria (R1-R10) and the follow-up change id
> that will repair them, including R8 renames. Do not edit the corpus in this
> change.

### Prompt 2 — Inventory personas

> Read Phase 2. Build the persona inventory: one row per persona file,
> reference, or topic copy with its deviation (identity-criteria collapse,
> schema gap, dangling reference, biography copy) and the follow-up change
> id. Confirm every planned merge with the user before recording it.

### Prompt 3 — Re-qualify ADRs

> Read Phase 3. For every accepted record, re-run the five dimensions, the
> three falsification tests, and the cheaper-home challenge; record the
> verdict and the audit note in this change, and give a failing record a row
> with its canonical destination and follow-up (rationale move, register and
> index removal). List every proposed record against its owning change; if
> the owner has archived, re-qualify it here or create a new named follow-up.
> Give a stale project-local ADR template a row whose follow-up deletes it
> and re-enables arc42.

### Prompt 4 — Inventory the smaller adoptions

> Read Phase 4. Build rows for change seeds (one of the five statuses plus
> the content schema) and for missing `(open: Q<N>)` qualifiers and `D<n>`
> ledger entries. Re-run every existing `confirmed` term's search and record
> the commands and hit counts in its collision-check cell (the one direct
> edit this change makes); a collision becomes a follow-up row. Read
> `givn instructions dialog` and re-read the lint severity and route
> confidence output; no rows for those.

### Prompt 5 — Inventory ejected overrides

> Read Phase 5. List every override carrying pre-0.8.0 rule text or a stale
> default as a row with a follow-up that re-ejects it and re-applies only
> genuine project-specific edits.

### Prompt 6 — Validate and archive

> Confirm this change edited no corpus artifact except the term
> collision-check cells, every row names a follow-up change or an in-flight
> one, and no archived change is named as pending. Run `givn lint` and
> `givn check review`; resolve or explicitly record every `[PERS ]` advisory.
> Run the project's suite. Commit the inventory and archive the maintenance
> change through the normal flow; the follow-up changes then proceed as
> normal work.

## Completion boundary

The maintenance change is complete when every permanent use case, persona,
accepted ADR, term record, R8 name, seed, and ejected override has an
inventory row with a disposition and a named or in-flight follow-up change,
and the collision-check cells carry their re-run evidence. The migration
itself is complete when every follow-up change has archived through the
normal gates.
